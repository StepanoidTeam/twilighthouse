# Рефакторинг логики перков

## Зачем

Сейчас часть логики перков живёт в `run-perks.js`, часть в игровых модулях, часть в `State`.
Из-за этого эффекты начинают размазываться по проекту:

- глобальный `State` получает поля, которые нужны только одному перку;
- `run-perks.js` становится местом, где смешаны выбор перков, стаки, XP и конкретные эффекты;
- временные эффекты сложнее сбрасывать и тестировать;
- новые перки могут требовать правок в нескольких несвязанных файлах.

Цель рефакторинга: оставить `run-perks.js` диспетчером прогресса и выбора, а поведение каждого перка вынести в изолированный модуль.

## Базовая идея

Каждый перк описывается как небольшой контроллер со своим жизненным циклом:

```js
export const oldMapPerk = {
  id: 'old_map',
  apply(ctx) {},
  update(ctx, delta) {},
  reset(ctx) {},
};
```

Где:

- `apply(ctx)` вызывается, когда игрок выбрал перк.
- `update(ctx, delta)` вызывается каждый игровой тик, если перку нужна активная логика.
- `reset(ctx)` вызывается при новом забеге, выходе в меню или очистке игры.

Для перков без активной логики достаточно `apply()`.
Для пассивных множителей можно оставить чистые функции, но держать их рядом с определением перка.

## Что должно остаться в State

В `State` должны оставаться только данные, которые реально нужны нескольким системам игры.

Примеры нормальных полей:

- `runPerkStacks`
- `runLampMult`
- `runBeamMult`
- `runPoliceSpeedMult`
- общий флаг визуального слоя, если им пользуются разные системы, например `oldMapIndicatorsActive`

Примеры того, что лучше не хранить в `State`:

- приватные таймеры одного перка;
- внутренние cooldown-флаги;
- временные счётчики, которые не нужны UI, сохранениям или другим системам;
- одноразовые ссылки на объекты, которыми владеет конкретный модуль.

Такие данные должны жить внутри модуля перка или эффекта.

## Пример: Старая карта

Текущая правильная граница:

- `State.oldMapIndicatorsActive` — общий флаг, который включает слой индикаторов. Его может включать туториал или перк.
- таймер действия старой карты — приватная переменная внутри `old-map.js`, потому что он нужен только эффекту карты.
- `triggerOldMapReveal(durationMs)` — публичный API эффекта.
- `resetOldMapReveal()` — очистка эффекта.

В будущем это можно оформить как контроллер:

```js
export const oldMapPerk = {
  id: 'old_map',

  apply() {
    triggerOldMapReveal(OLD_MAP_REVEAL_MS);
  },

  update() {
    updateOldMapReveal();
  },

  reset() {
    resetOldMapReveal();
  },
};
```

Важная мысль: туториал не является перком, но может переиспользовать тот же визуальный слой через общий флаг.
При этом таймер перка не должен попадать в `State`.

## Предлагаемая структура файлов

Вариант без большого переезда сразу:

```text
js/run-perks.js
js/perks/
  old-map.perk.js
  occult-lamp.perk.js
  new-icebergs.perk.js
  repair-lighthouse.perk.js
  index.js
```

`js/perks/index.js` экспортирует реестр:

```js
export const RUN_PERKS = {
  old_map: oldMapPerk,
  occult_lamp: occultLampPerk,
  new_icebergs: newIcebergsPerk,
  repair_lighthouse: repairLighthousePerk,
};
```

`run-perks.js` тогда отвечает за:

- XP;
- выбор доступных перков;
- стаки;
- проверку max stacks;
- вызов `RUN_PERKS[perkId]?.apply(ctx)`;
- вызов `update()` и `reset()` для зарегистрированных перков.

## Контекст перка

Чтобы не импортировать всё подряд, можно передавать небольшой `ctx`.

Пример:

```js
const ctx = {
  state: S,
  spawnTooltip,
  updateHUD,
  now: () => performance.now(),
};
```

На первом этапе можно не вводить строгий `ctx` и оставить прямые импорты в модулях перков.
Главное - отделить владение логикой перка от общего `run-perks.js`.

## План миграции

1. Оставить текущий `run-perks.js` как публичный API для UI и геймплея.
2. Вынести перки с явными side effects:
   - `old_map`;
   - `occult_lamp`;
   - `new_icebergs`;
   - `repair_lighthouse`.
3. Добавить реестр `RUN_PERKS`.
4. Заменить `onPerkApplied(perkId)` на вызов контроллера из реестра.
5. Добавить общий `updateRunPerks(delta)` только для перков, которым нужен тик.
6. Добавить общий `resetRunPerkEffects()` для очистки приватных эффектов.
7. После этого аккуратно переносить пассивные множители ближе к определениям перков.

## Правило для новых перков

Если новый перк добавляет поле в `State`, сначала нужно ответить:

- это поле нужно нескольким системам или только этому перку?
- должно ли оно переживать reset, pause, выход в меню?
- нужно ли UI читать его напрямую?
- можно ли держать это как приватное состояние модуля?

Если поле нужно только одному перку, оно не должно попадать в `State`.
